# VirtueMart Database Analysis — Libertí Dancewear (libertidance.com)

**Purpose:** reverse-engineering investigation of the production SQL dump, to prepare a Python
product importer that writes directly to the Joomla/VirtueMart database.

**Source:** `support_antima_.sql` (phpMyAdmin dump, 12.5 MB).
Note: the file is named `support_antima_` but the dump itself contains
`CREATE DATABASE support_manouka_` / `USE support_manouka_` — same database, file name mismatch only.

**Method:** the dump was loaded into a **local throwaway SQLite copy** (converted by a throwaway
parser script; the original dump was not modified). All queries below are read-only against that
copy. No production system was touched.

Verified environment (from dump itself, not assumed):

| Joomla | 5.4.8 | dump header |

Scale: 431 products, 431 price rows, 10,670 product-customfield rows, 1,284 media rows, 43 categories.

## 1. Executive summary

* A product is **spread over ~8 tables**. The core row in `virtuemart_products` holds only
  language-independent data (SKU, stock, flags, published, timestamps). **All names and
  descriptions live in per-language clone tables** (`…_en_gb`, `…_el_gr`), one row per product
  per language — both always exist in this dump (431/431/431).
* **Prices are stored net (VAT-exclusive).** A single global calc rule (id 1, `VatTax`, `+24%`,
  no restrictions) turns net → gross. CD004: net `77.82258` × 1.24 = `96.50` gross. ✔
* **Size / Colour / Fabric are plain VirtueMart string custom fields** (`field_type='S'`,
  custom ids 6 / 7 / 10). Each choice is **one row** in `virtuemart_product_customfields`
  with a string in `customfield_value`. Multiple sizes = multiple rows. No JSON, no serialization.
* `customfield_price` is a **net surcharge** (VAT-exclusive), not a variant price. Proof below.
* Images are **files on disk** referenced by relative URL (`images/stories/virtuemart/product/…`)
  through `virtuemart_medias` + `virtuemart_product_medias`. Nothing binary in the DB. Thumbs are
  generated by VM (mostly empty `file_url_thumb`).
* The site also uses the **"VM Custom Advanced" plugin** (customs 13/14/19/20, tables
  `xhngw_vmcustomadvanced_*`) for Fabric×Colour combo selection on other products. **It is not
  needed for the importer's scope** (Size/Colour/Fabric strings) and must not be touched.
* Two conventions to respect: every `product_customfields.published` is **0** in this dump
  (10,670/10,670) and products still display their options — the importer must write **0** too,
  not 1. `product_tax_id` is 1 on 292 price rows and 0 on 140 (incl. CD004); the global rule
  applies either way — write **1** explicitly to be safe.
* Categories are assigned via a simple join table; CD004 is in one category (62 Λάτιν/Latin,
  child of 24 Παπούτσια/Shoes). Products need ≥ 1 category, so the importer must at least
  *assign existing* categories; full category creation is **not** required.
* The shop was previously imported/managed with **CSVI** (`xhngw_csvi_*` tables present) —
  useful context; several products (incl. CD004, all `ordering=0`) bear its fingerprints.

## 2. Database/schema overview

181 tables. Joomla core tables (assets, content, categories, users, …) coexist with
`xhngw_virtuemart_*` (VirtueMart), `xhngw_csvi_*` (CSVI import component),
`xhngw_vmcustomadvanced_*` (VM Custom Advanced plugin), `xhngw_vpframework_*` (VP Framework
template plugin).

Two architectural patterns matter:

1. **VM language-clone pattern.** Any entity with text has a core table + one clone table per
   active language, suffix = lowercase lang code (`el-GR → _el_gr`, `en-GB → _en_gb`).
   The clone table's PK is the *same id* as the core table (1:1, no separate language id column).
   Affected product tables: `products`, `categories`, `manufacturers`, `vendors`
   (payment/shipment methods too — irrelevant here).
2. **Calc-rule pattern for pricing.** No gross price is stored anywhere. Net price + calc rules
   (`virtuemart_calcs`) compute gross at render/cart time.

## 3. Relevant tables

Legend: **I** = importer INSERTs, **U** = importer UPDATEs, **R** = read-only reference.

### `xhngw_virtuemart_products` — I/U
Core product row. PK `virtuemart_product_id` (int, auto-increment).

Important columns: `product_sku` (unique in practice; CD004's GTIN column also holds "CD004"),
`product_parent_id` (**0 for all 431 products** — no child/variant products in this shop),
`virtuemart_vendor_id` (always 1), `product_in_stock`, `product_ordered`,
`product_available_date`, `product_weight`/`_uom`, `product_special`, `product_discontinued`,
`published`, `pordering`, `product_params` (default string, see §11), and VM-maintained cache
flags `has_categories`, `has_manufacturers`, `has_medias`, `has_prices`, `has_shoppergroups`
(CD004: 1,1,1,1,0). Timestamps `created_on/created_by/modified_on/modified_by` (user 119 =
Joomla user "Liberti Dancewear"/libertidance), `locked_on/locked_by` (always empty).

### `xhngw_virtuemart_products_en_gb` / `xhngw_virtuemart_products_el_gr` — I/U
Translations. PK `virtuemart_product_id`, 1:1 with core.
Columns: `product_name`, `product_s_desc` (short), `product_desc` (HTML), `metadesc`, `metakey`,
`customtitle`, `slug` (URL segment; unique per table — verified no dupes; identical slugs across
the two languages are normal, e.g. `cd004`/`cd004`).

### `xhngw_virtuemart_product_prices` — I/U
PK `virtuemart_product_price_id`. One row per product in this shop (432 rows / 431 products;
exactly one product has 2). Columns: `virtuemart_product_id`, `virtuemart_shoppergroup_id`
(**0** on all 432 rows = default price for all shopper groups),
`product_price` (decimal(15,6), **net**), `override` (0), `product_override_price` (0),
`product_tax_id` (0 or 1), `product_discount_id` (0), `product_currency` (47),
`price_quantity_start/end` (0), timestamps.

### `xhngw_virtuemart_calcs` — R (never INSERT)
PK `virtuemart_calc_id`. Exactly **one** rule in this installation:
`id=1, calc_name='VAT 24%', calc_kind='VatTax', calc_value_mathop='+%', calc_value=24,
published=1`, and `has_categories/has_shoppergroups/has_manufacturers/has_countries/has_states`
all **0** with empty attachment tables (`calc_categories`, `calc_countries`,
`calc_shoppergroups`, `calc_states`) → **global rule applying to every product**. There is no
per-category tax anywhere.

### `xhngw_virtuemart_currencies`, `xhngw_virtuemart_shoppergroups` — R
Currency 47 = EUR. Shopper group 1 = default ("-default-"); price rows reference shoppergroup 0
(= "all/default"). Vendor currency = 47.

### `xhngw_virtuemart_customs` — R (definitions exist; do not redefine)
PK `virtuemart_custom_id`. The relevant definitions:

| id | custom_title | field_type | custom_element | is_cart_attribute | layout_pos | published |
|----|--------------|-----------|----------------|-------------------|------------|-----------|
| 6  | COM_VMCUSTOMADVANCED_SETS_SIZE  | S (string) | (empty) | 1 | addtocart | 1 |
| 7  | COM_VMCUSTOMADVANCED_SETS_COLOR | S (string) | (empty) | 1 | addtocart | 1 |
| 10 | COM_VMCUSTOMADVANCED_SETS_FABRIC| S (string) | (empty) | 1 | addtocart | 1 |

Titles are Joomla language keys (translated at render). `custom_params` for 6/7/10:
`addEmpty="0"|selectType="0"|multiplyPrice="0"|transform=""|product_sku=""|product_gtin=""|product_mpn=""||`.
Note `multiplyPrice="0"` (= absolute money modifier, not %) in the plugin param string.

Other customs present (1 related products, 2 related categories, 3/4 groups, 5 Specification,
8 Multi Variant, 9 Generic Variant, 11 Layers, 15 Length, 16 Box size, 17 Hardness, 18 Heel,
13/14/19/20 = plugin "advanced", see §5).

### `xhngw_virtuemart_product_customfields` — I/U
PK `virtuemart_customfield_id` (auto-increment). One row per product-per-option.
Columns: `virtuemart_product_id`, `virtuemart_custom_id` (→ customs),
`customfield_value` (varchar 2500, **the string value**, e.g. "35", "BLK", "Cotton & Mousseline"),
`customfield_price` (decimal(15,6), **net surcharge**, 0 = no surcharge),
`customfield_params` (for customs 6/7/10 **always exactly** `product_sku=""|product_gtin=""|product_mpn=""||`),
`disabler`/`override`/`noninheritable` (all 0 here), `published` (**0 on all 10,670 rows**),
`ordering` (0 on CSVI-imported rows like CD004; 0..N sequence on admin-entered products, e.g.
product 36 has orderings 0–11 across its customs), `product_sku/gtin/mpn` (NULL here),
timestamps. UNIQUE index on (customfield_id, product_id, custom_id, customfield_value(200)).

### `xhngw_virtuemart_medias` — I/U
PK `virtuemart_media_id`. Columns: `file_title`, `file_mimetype` (`image/jpeg`),
`file_type` (**`product`** for product images; also category/manufacturer/vendor),
`file_url` (**relative** path from Joomla root, e.g. `images/stories/virtuemart/product/CD004 Black 0.jpg`),
`file_url_thumb` (empty on 1,251 of 1,284 rows — VM generates thumbs on the fly),
`file_is_product_image` (0 everywhere), `is_image` (1 for images), `published` (1), `shared` (0),
`file_params` (empty), timestamps.
No two media rows share a `file_url` (dedupe point), but one media row can be attached to
several products.

### `xhngw_virtuemart_product_medias` — I/U
Join table. PK `id`. Columns: `virtuemart_product_id`, `virtuemart_media_id`,
`ordering` (**1-based**; first row = main/primary product image). UNIQUE(product, media).

### `xhngw_virtuemart_product_categories` — I/U
Join table. PK `id`. Columns: `virtuemart_product_id`, `virtuemart_category_id`, `ordering` (0).
UNIQUE both ways (product, category) and (category, product).

### Category cluster — R (assignment only)
`xhngw_virtuemart_categories` (PK `virtuemart_category_id`; `category_parent_id`, `published`,
`ordering`, `shared`, `has_children`, `has_medias`, timestamps; **no name column**) +
`…_categories_en_gb` / `…_categories_el_gr` (`category_name`, `category_description`, `metadesc`,
`metakey`, `customtitle`, `slug`) + `xhngw_virtuemart_category_categories` (adjacency tree:
`category_parent_id`, `category_child_id`, `ordering`). The parent link is stored **twice**
(column on core row *and* tree row) — a classic source of breakage if written naively.

### `xhngw_virtuemart_product_manufacturers` — I (only if a manufacturer applies)
PK `id`, UNIQUE(product, manufacturer). CD004 → manufacturer **15** ("Go Dance", names/slugs in
`manufacturers_en_gb`/`_el_gr`). 429 of 431 products have a manufacturer. The importer should
assign an existing manufacturer id.

### Plugin cluster (system 2, out of scope) — R/never
`xhngw_vmcustomadvanced_sets` (5 global option groups: 1=Fabric, 2=Colour, 3=Size,
4=Color Pattern, 5=Heel), `xhngw_vmcustomadvanced_options` (153 global options with
title/alias lang-key/HEX color), `xhngw_vmcustomadvanced_order_items` (per-order variant
tracking). Consumed by customs 13/14/19/20 (`field_type='E'`, `custom_element='advanced'`).

### Never touch — R
`virtuemart_orders`, `virtuemart_order_items`, `virtuemart_order_calc_rules`,
`virtuemart_order_histories`, `virtuemart_order_item_histories`, `virtuemart_order_userinfos`,
`virtuemart_invoices`, `virtuemart_ratings*`, `virtuemart_rating_reviews`, `virtuemart_carts`,
`virtuemart_waitingusers`, `virtuemart_vmcustomadvanced_order_items`, `virtuemart_migration_oldtonew_ids`,
Joomla `assets`, `ucm_content`, `finder_*` (search index is rebuilt by Joomla, not by hand).

## 5. Custom field architecture

**Two distinct systems coexist.** The importer only needs system 1.

### System 1 — plain string customs (REQUIRED): Size=6, Colour=7, Fabric=10

* **Definition:** one row in `virtuemart_customs` (see table in §3). Field type `S`
  ("string"), `is_cart_attribute=1`, `is_input=1`, cart position `addtocart`.
  No `custom_element` → core VirtueMart handles it, no plugin involved.
* **Product reference:** a row in `virtuemart_product_customfields` per value:
  `virtuemart_custom_id` = 6/7/10, `customfield_value` = the string.
* **Multiple Size values:** multiple rows with the same `virtuemart_custom_id=6`, one per size
  (CD004: 8 rows "35"…"42"). Order of rows = `ordering` (0/blank on CD004 — the frontend then
  falls back to `virtuemart_customfield_id` order; admin-entered products use 0..N).
* **Multiple Colour values:** same pattern, custom_id=7 (e.g. product 24 has rows
  "24 Lemon Yellow", "31 Watermelon Pink", "43 Mouse Grey").
* **Fabric:** same pattern, custom_id=10 (e.g. product 24: "Cotton & Mousseline" price 0,
  "Lycra & Mousseline" price 2.016). 129 rows over 109 products.
* **Storage format:** plain scalar strings in normal rows. **No JSON, no serialized data**
  (the only JSON in this table belongs to system 2, inside `customfield_params`).
* **Price with a value:** yes — column `customfield_price` (see §6).
* **Published:** 0 for every row (see §10).

### System 2 — "VM Custom Advanced" plugin (NOT required, do not write)

Customs 13 (VP Fabric/Colour), 14 (VP Color Texture), 19 (Shoe Size), 20 (VP Size/Heel):
`field_type='E'`, `custom_element='advanced'`. Global option catalog in
`vmcustomadvanced_sets` (sets 1..5) + `vmcustomadvanced_options` (153 options; e.g. set 2
option 19 = "01 White" #ffffff, option 20 = "09 Black" #000000). A per-product row for custom 13
has `customfield_value=''` and a JSON blob in `customfield_params`:

```json
stock="0"|ordered="0"|sets={ "1": "2", "2": "19" }
```

= one selectable combination: set 1 (Fabric) option 2 ("Lycra") + set 2 (Colour) option 19
("01 White"). 6,426 such rows on 143 products; 3,452 carry a surcharge. Order-time variant
tracking in `vmcustomadvanced_order_items`. **Do not create these rows** for the string-based
Size/Colour/Fabric workflow; mixing systems on one product is what the shop does manually, not
what the importer should replicate.

## 6. Price architecture

### Product price

* Stored **net** (VAT-exclusive) in `virtuemart_product_prices.product_price`, decimal(15,6).
* Gross is never stored. It is computed at display/cart time from calc rules.
* This shop has exactly one rule: **calc 1 = "VAT 24%", kind VatTax, +24 %, global**
  (no category/country/shoppergroup restrictions — verified empty attachment tables).
* `product_tax_id`: 292 rows → 1 (rule explicitly attached), 140 rows → 0 (incl. CD004; the
  global rule still applies). **Importer should write `product_tax_id = 1`** — it is the
  explicit, unambiguous form and matches the majority of rows.
* `product_currency = 47` (EUR) on all rows. `override=0`, `product_override_price=0`,
  `product_discount_id=0`, `price_quantity_start=end=0` everywhere.
* Cross-check on real data: net 77.82258 × 1.24 = 96.50 ✔ (matches the developer's example
  exactly); product 24: net 28.22581 × 1.24 = 35.00 ✔. All 431 product nets × 1.24 land on
  clean €X.YZ values.

### Custom-field (variant) price

`virtuemart_product_customfields.customfield_price` — the decisive findings:

1. **It is a surcharge, not a variant price.** All non-zero values are small (0.4 – 19.755)
   relative to the product net (ratios 0.009 – 0.25). **Zero rows** anywhere in the table equal
   their product's net price (checked |cf_price − product_price| < 0.01 → 0 matches).
2. **It is net (VAT-exclusive).** Every distinct value × 1.24 lands on a clean 0.50-step gross
   amount:

   | stored (net) | × 1.24 | intended gross |
   |---|---|---|
   | 0.403 / 0.405 / 0.4 | ≈0.50 | €0.50 |
   | 0.806 / 0.81 | ≈1.00 | €1.00 |
   | 1.209 / 1.21 | ≈1.50 | €1.50 |
   | 1.61 / 1.615 | ≈2.00 | €2.00 |
   | 2.015 / 2.016 / 2.02 | ≈2.50 | €2.50 |
   | 2.419 / 2.42 | ≈3.00 | €3.00 |
   | 4.032 | ≈5.00 | €5.00 |
   | 4.435 | ≈5.50 | €5.50 |
   | 12.096 | ≈15.00 | €15.00 |

   The several stored spellings of one gross value (0.403/0.405/0.4 → 0.50) show the admin
   enters a gross figure and VM divides by 1.24 (with rounding noise), i.e. VM stores net.
3. **Semantics by field:** Size surcharges (product 356: sizes 34–39 → 2.42, sizes 40–43 →
   4.435 = +€3.00/+€5.50 gross per big size), Fabric surcharges (Lycra options → +€2.00–15.00
   gross), custom 13 combo surcharges (same pattern).
4. **Colour (custom 7): all 1,593 rows have `customfield_price = 0`.** No colour-based price
   difference exists anywhere in the current data.

**On the developer's statement** — "when entering a Colour custom-field value, a price equal to
the product price minus VAT may need to be entered":

`UNKNOWN — needs confirmation`

The dump **contradicts the literal reading** ("store the product's net price in the colour row"):
no such row exists. What the data *does* support is that custom-field prices are stored
**net, as surcharges**; if the developer meant "enter values in net terms (product price minus
VAT logic applies)", that matches the storage evidence. The Python importer must be told, per
input field, whether a supplied amount is gross or net; the database itself stores
**net surcharge**. Ask the developer to confirm with one live example in the VM admin
(see §12, Q1).

## 7. Multilingual architecture

* Mechanism: **VirtueMart native per-language clone tables** — no Joomla associations
  (`xhngw_associations` contains no VM rows), no Falang, no language id column. The clone row's
  `virtuemart_product_id` **is** the core product id.
* Active languages (VM config `active_languages`): **el-GR, en-GB** → tables
  `xhngw_virtuemart_products_el_gr` and `xhngw_virtuemart_products_en_gb`.
  Joomla site default = el-GR, admin default = en-GB (`com_languages` params). `de-DE` disabled.
* Language-dependent fields (per table): `product_name` (title), `product_desc` (HTML),
  `product_s_desc` (short), `metadesc`, `metakey`, `customtitle`, `slug`.
  Same slug in both tables is fine (URLs are language-scoped).
* Language-independent (core `virtuemart_products` + everything else): SKU, stock, weight,
  dates, published, prices, custom-field values, media, categories, manufacturer links.
* **Both rows always exist**: 431 core / 431 en_gb / 431 el_gr. A bilingual product =
  1 core row + exactly 1 row in each clone table. The importer must INSERT/UPDATE **both**,
  even if one language's copy is a fallback duplicate of the other.
* Custom-field values ("BLK", "9.0cm Plated Heel") are stored **once**, not per language —
  the Greek shop page shows the same string. If Greek values are wanted later, that is a
  change of convention (see §12, Q3).

## 8. Image/media architecture

* **Files live on disk, DB stores references.** No blobs anywhere.
* Physical location (from VM config `media_product_path` + leaked absolute path):
  `/home/support/web/libertidance.com/public_html/images/stories/virtuemart/product/`
  (`media_category_path` …/category/, `media_manufacturer_path` …/manufacturer/,
  `media_vendor_path` …/vendor/).
* DB rows:
  * `virtuemart_medias`: one row per image file. `file_url` = path **relative to Joomla root**
    (`images/stories/virtuemart/product/CD004 Black 0.jpg` — note: spaces in filenames are
    permitted and occur). `file_title` ≈ filename, `file_mimetype` `image/jpeg`,
    `file_type='product'`, `is_image=1`, `published=1`, `shared=0`, `file_is_product_image=0`.
  * `virtuemart_product_medias`: join row per (product, image) with **1-based `ordering`;
    ordering = 1 is the main/primary image** (CD004: "CD004 Black 0.jpg" is ordering 1).
    UNIQUE constraints both ways.
* Thumbs: `file_url_thumb` empty on 1,251/1,284 rows → VM 4 generates resized thumbs at runtime
  (into `images/stories/virtuemart/product/resized/`). The importer does **not** need to create
  thumbnails; it must ensure the source file is readable by PHP.
* No duplicate `file_url` media rows exist → importer dedupe rule: **look up `file_url` first;
  if a media row exists, reuse its id; else INSERT.** (One media row may then be attached to
  several products — precedented: `syllabus_1.jpg`, `soho_*.jpg` are attached to 2 products.)
* What the future importer must do with local image files:
  1. copy/upload the file into `images/stories/virtuemart/product/` (via SFTP/SSH — the DB
     cannot carry the bytes);
  2. INSERT `virtuemart_medias` (or reuse by `file_url`);
  3. INSERT `virtuemart_product_medias` with `ordering` 1..N in the desired gallery order
     (1 = main);
  4. UPDATE `virtuemart_products.has_medias = 1`.

## 9. Category architecture

* Products ↔ categories: `xhngw_virtuemart_product_categories` (product_id, category_id,
  ordering; both-direction UNIQUE). CD004: one row → category 62.
* Category 62 "Λάτιν"/"Latin" sits under category 24 "Παπούτσια"/"Shoes" under root (0).
* The tree is stored in **two places** that must agree: `virtuemart_categories.category_parent_id`
  and the `virtuemart_category_categories` adjacency row (parent 24 → child 62, id 65).
  Denormalized flags `has_children`, `has_medias` sit on the core row.
* Names/descriptions/slugs in `…_categories_en_gb` / `…_categories_el_gr`.
* 43 categories, all flat two-level (root → Shoes/… → leaf), `published=1`, `shared=0`.
* **Importer requirement:** a product with no category is invisible in VM listing/navigation;
  every product row here has ≥1 category (489 join rows / 431 products). The importer must
  **assign existing category ids** (passed in per product). Creating new categories is *not*
  required by the task and is deliberately out of scope (it would require touching the
  dual-stored tree + flags).

## 10. Published/unpublished behavior

* Product visibility: **`xhngw_virtuemart_products.published`** (tinyint). Current data:
  410 × 1, 21 × 0. `product_special` (featured) and `product_discontinued` are separate flags.
  → **Importer must create products with `published = 0`**; they then appear in the VM admin
  product list but are not visible/buyable in the shop until staff flips the toggle in Joomla.
* Media: `virtuemart_medias.published` = 1 on all used product images → importer writes 1.
* Product customfields: `virtuemart_product_customfields.published` = **0 on all 10,670 rows**
  — including rows that demonstrably render in the shop (sizes/colours are sold daily).
  In this VM 4.8.0 installation the frontend does not filter option rows by this flag, and the
  admin/CSVI flow leaves it at 0.
  `UNKNOWN — needs confirmation` (why it is 0; whether a VM update will ever start filtering
  it) — **but the safe move is to match the observed convention: write 0**, never 1.
* Customs definitions (6/7/10): `published=1` — do not change.

## 11. Importer implications (dangerous fields & rules)

**Do not fabricate or reuse IDs**
* All PKs (`virtuemart_product_id`, `virtuemart_product_price_id`, `virtuemart_customfield_id`,
  `virtuemart_media_id`, join-table `id`s) are MariaDB AUTO_INCREMENT — INSERT without the id
  column and fetch `last_insert_rowid()`/`LAST_INSERT_ID()`. Never renumber, never INSERT
  explicit ids below the current AUTO_INCREMENT watermarks.
* Look up entities by natural keys: product by `product_sku`; custom field by
  `virtuemart_custom_id` (6/7/10 — hardcode after verifying); media by `file_url`;
  category by id from configuration.

**VM-maintained cache flags (break listings if wrong)**
* `products.has_categories / has_manufacturers / has_medias / has_prices / has_shoppergroups`:
  set to match what you actually created (CD004 pattern: 1,1,1,1,0). Wrong 0s hide data in admin;
  wrong 1s create ghost links.

**Convention strings that must be copied verbatim**
* `product_params` default: `min_order_level=""|max_order_level=""|step_order_level=""|shared_stock=0|product_box=""`
* `customfield_params` for customs 6/7/10: `product_sku=""|product_gtin=""|product_mpn=""||`
* `product_sku`/`product_gtin`/`product_mpn` columns on customfield rows: NULL in this data.

**IDs that are configuration, not data**
* vendor = 1, currency = 47, calc (tax) = 1, shoppergroup = 0 on price rows, customs = 6/7/10.
  Never INSERT into `virtuemart_calcs`, `virtuemart_currencies`, `virtuemart_shoppergroups`,
  `virtuemart_customs`.

**Timestamps / users**
* `created_on` + `created_by=119` (Liberti Dancewear admin) on first INSERT;
  `modified_on` + `modified_by` on every UPDATE. `locked_on/locked_by` always empty.
  Timestamps exist on products, prices, customfields, medias — fill them; VM admin displays them.

**Ordering columns**
* `product_medias.ordering` 1-based, defines main image — control it deliberately.
* `product_categories.ordering` = 0 everywhere — keep 0.
* `product_customfields.ordering`: 0 is accepted (CD004/CSVI style); if the shop wants a
  specific option order, write 0..N in row sequence.

**Slugs**
* Unique per language table. Derive from product name (lowercase, transliterate Greek for the
  el_gr slug **or** copy the en slug — both patterns exist; `cd004` and `latin-shoes` are
  identical in both languages). Must not collide within the same table.

**Adjacent systems to leave alone**
* `xhngw_vmcustomadvanced_*` (plugin), `xhngw_csvi_*` (CSVI), order/invoice/rating/cart tables,
  `virtuemart_migration_oldtonew_ids`, Joomla `assets`/`finder_*`/`ucm_*`.
* 31 orphan `product_customfields` rows with `virtuemart_product_id=0` (junk) — ignore, don't
  "clean up" from the importer.
* `virtuemart_waitingusers`, `virtuemart_product_shoppergroups` (empty/unused here).

**Multisite/language safety**
* One vendor, one currency, no shoppergroup-specific prices → importer can ignore those
  dimensions, but must still write `virtuemart_shoppergroup_id=0` and `product_currency=47`
  explicitly on price rows.

## 12. Unknowns / questions for Joomla developer

1. **Custom-field price input convention** — `UNKNOWN — needs confirmation`. Data proves
   `customfield_price` is stored as a **net (VAT-exclusive) surcharge** (all values × 1.24 =
   clean 0.50-step gross amounts). The statement "a price equal to the product price minus VAT
   may need to be entered" does not match any stored row (no colour/fabric row stores the
   product's net price). Question: when the shop manager enters a Colour/Fabric price in the VM
   admin, is the typed number gross (VM divides by 1.24) or net (stored as typed)? And for
   *new* importer-supplied colours — should they always be 0 (all existing colour rows are 0)?
2. **`product_customfields.published = 0` convention** — `UNKNOWN — needs confirmation`.
   All 10,670 rows are 0 yet options render and sell. Confirm the frontend really ignores this
   flag in this VM build (theme/plugin override?) so the importer may safely write 0.
3. **Greek values for Size/Colour/Fabric strings** — values are stored once (language
   independent). The Greek site currently shows e.g. "BLK", "9.0cm Plated Heel" untranslated.
   Is that intended for imported products too, or should the importer receive per-language
   option labels (which would need a convention change — e.g. two rows or Greek-titled values)?
4. **Whether imported products should carry a manufacturer** — 429/431 products have one
   (CD004 → "Go Dance", id 15). Which manufacturer id should the importer assign for new
   products?
5. **GTIN column reuse** — `product_gtin` currently holds the SKU ("CD004"). Copy that
   convention or leave NULL?
6. **Stock policy** — CD004 has `product_in_stock=30`, `product_stockhandle='0'` (VM default
   handling). Confirm importer should always write `product_stockhandle='0'` and treat stock as
   a plain integer.

## 14. Proposed high-level import transaction for one product

All steps run in **one DB transaction** (InnoDB); any failure → full ROLLBACK.
Reads first (steps 1–2 lookups) then writes. `vendor=1`, `currency=47`, `tax=1`,
`customs 6/7/10` are configuration constants verified in §3.

```text
 1. Find product by SKU
      SELECT virtuemart_product_id FROM xhngw_virtuemart_products WHERE product_sku = :sku
      → existing id ⇒ UPDATE flow; none ⇒ INSERT flow

 2. Create/update product (core row)
      xhngw_virtuemart_products                      INSERT or UPDATE
        (sku, vendor 1, parent 0, stock, dates, params string,
         published=0 for new; set has_prices=1 has_medias=1
         has_categories=1 has_manufacturers=? accordingly)

 3. Create/update English data
      xhngw_virtuemart_products_en_gb                INSERT or UPDATE (1:1 with step 2 id)
        (product_name, product_s_desc, product_desc, metadesc, metakey,
         customtitle, slug — unique in this table)

 4. Create/update Greek data
      xhngw_virtuemart_products_el_gr                INSERT or UPDATE (same id)
        (same columns, Greek values, slug)

 5. Create/update price
      xhngw_virtuemart_product_prices                UPDATE existing row or INSERT
        (product_id, shoppergroup 0, product_price = NET,
         product_tax_id = 1, product_discount_id 0, currency 47,
         override 0, qty 0–0, timestamps)

 6. Create/update Size values (custom 6)
      xhngw_virtuemart_product_customfields          diff rows for (product_id, custom_id=6):
        delete removed · update changed values · insert new
        (customfield_value = size string, customfield_price = net surcharge or 0,
         customfield_params = 'product_sku=""|product_gtin=""|product_mpn=""||',
         disabler 0, override 0, noninheritable 0, published 0, ordering 0..N)

 7. Create/update Colour values (custom 7)
      xhngw_virtuemart_product_customfields          same diff logic, custom_id=7
        (existing convention: customfield_price = 0 for all colour rows)

 8. Create/update Fabric (custom 10)
      xhngw_virtuemart_product_customfields          same diff logic, custom_id=10
        (customfield_price = net surcharge or 0)

 9. Copy/register images (files on disk first, via SFTP/SSH:
      copy into /…/public_html/images/stories/virtuemart/product/)
      xhngw_virtuemart_medias                        for each new image file:
        SELECT virtuemart_media_id WHERE file_url = :rel_path   (dedupe)
        else INSERT (file_title, file_mimetype, file_type='product',
        file_url = rel path, file_url_thumb='', is_image=1,
        file_is_product_image=0, published=1, shared=0)

10. Create/update product–media relationships
      xhngw_virtuemart_product_medias                replace set for product:
        (product_id, media_id, ordering = 1..N, 1 = main image)
      + xhngw_virtuemart_products.has_medias = 1

11. Set published = 0
      xhngw_virtuemart_products.published = 0        (also: do NOT touch
        xhngw_virtuemart_product_customfields.published — write 0 on new rows,
        matching the shop-wide convention)

12. Commit
      UPDATE modified_on/modified_by = 119 on every touched table before COMMIT;
      COMMIT; then (outside DB) verify via the §4 trace queries + optionally
      trigger Joomla cache cleanup — no other tables are written.
```

Tables the transaction touches: `xhngw_virtuemart_products`,
`xhngw_virtuemart_products_en_gb`, `xhngw_virtuemart_products_el_gr`,
`xhngw_virtuemart_product_prices`, `xhngw_virtuemart_product_customfields`,
`xhngw_virtuemart_medias`, `xhngw_virtuemart_product_medias` (+1 category assignment if new:
`xhngw_virtuemart_product_categories`). Nothing else.
